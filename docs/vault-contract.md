# Vault contract

How secrets are stored, who can read them and how they reach a container. The
implementation is in `vault/` and `scripts/`; this is the agreement they follow.

## Architecture

```
Vault (one instance, run by the Identity team)
  ▲  AppRole login + read, over TLS
Vault Agent (one per consumer, sidecar)
  │  renders the secret as a file into a tmpfs volume
  ▼
consumer (reads a file; no Vault SDK, no Vault calls)
```

- **One Vault, one owner.** It is deployed apart from the application stack
  (`vault/server/docker-compose.yml`) so it stays up while the stack goes up and
  down. Teams are *clients* of it, never operators: policies only mean something
  when the client has no administrative rights over the server.
- **Reachability.** Vault is never published on a public interface
  (`VAULT_BIND_ADDR`: `127.0.0.1` locally, the Tailscale address of the server in
  the shared environment). Access from other machines goes through Tailscale, whose
  ACL lets each tagged team reach the Vault node on 8200 and nothing else.
- **Agents.** Each Agent sits alone on its own Docker network (`vault-<consumer>`):
  it can reach Vault and nothing can reach it. The Agent and its consumer share
  only a tmpfs volume, read-write for the Agent, read-only for the consumer.
- **TLS.** Private CA generated by `vault/tls/gen-certs.sh`; `ca.pem` is what every
  Agent trusts (`VAULT_CACERT`). It is public, but is handed over out of band, not committed.

## Namespaces (KV v2, mount `secret/`)

| Path | Holds | State |
|---|---|---|
| `secret/tpi/identity/*` | Identity's own secrets | in use |
| `secret/tpi/shared/clients/<team>` | client_credentials secret issued to a team | in use (`seed-service-client-v2.sh`) |
| `secret/tpi/<team>/*` | a team's private secrets and launch parameters; the team reads and writes its own | in use (`vault-onboard-team.sh`) |

Operators (`operator` policy) manage `identity/*` and `shared/clients/*`. They have
**no** access to `secret/tpi/<team>/*`.

## Identity secrets

| Vault path | Field | File the consumer reads | Consumer / how |
|---|---|---|---|
| `secret/tpi/identity/db` | `password` | `/run/secrets/config/db-password` | users-service, Spring Config Tree (`application.yml`) |
| | | `/run/secrets/db-password` | mysql (`MYSQL_ROOT_PASSWORD_FILE`), dev-mailbox (`DB_PASSWORD_FILE`) |
| `secret/tpi/identity/jwt` | `private_key` | `/run/secrets/jwt-private.pem` | users-service, `FileSystemSigningKeyProvider` (unchanged, DEC-18) |
| | `public_key` | `/run/secrets/jwks/dev.pem` | idem; the file name is the kid |
| `secret/tpi/identity/bootstrap` | `password` | `/run/secrets/config/admin-bootstrap-password` | users-service, Config Tree |
| `secret/tpi/identity/grafana` | `password` | `/run/secrets/admin-password` | grafana (`GF_SECURITY_ADMIN_PASSWORD__FILE`) |

## Policies and AppRoles

One AppRole per Agent, named like its policy, granting `read` on exactly the
paths above: `identity-users`, `identity-mysql`, `identity-dev-mailbox`,
`identity-grafana`. Tokens live 1 h (max 4 h) and the Agent renews them;
`secret_id` does not expire and is rotated on demand. `operator` is for the
Identity developers (userpass, 8 h tokens).

## Teams

`./scripts/vault-onboard-team.sh <team> [member ...]` sets a team up:

- policy `team-<team>` (from `vault/policies/team.hcl.tpl`): read and write on
  `secret/tpi/<team>/*`, read on `secret/tpi/shared/clients/<team>`;
- AppRole `<team>`, and its `secret_id` handed over **response-wrapped** (10 minutes, one use), so
  the first one to read it is the team;
- a userpass account `<team>-<member>` for each person who stores values by hand (UI or CLI), with
  a generated initial password printed once;
- an Agent config in `secrets/vault/teams/<team>/agent.hcl` (from `vault/agent/team-agent.hcl.tpl`).

Launch parameters and environment variables live in one secret, `secret/tpi/<team>/env` (one key per
variable). The team's Agent renders it as `/run/secrets/app.env`, plain dotenv, and
`vault/agent/load-env.sh` loads it into the process. Guide for teams: [vault-teams.md](vault-teams.md).

The Tailscale side (a tagged auth key per team) is done in the Tailscale console.

## Operating it

```bash
# once: certificates, server, bootstrap
./vault/tls/gen-certs.sh [<tailscale-hostname-or-ip>]
docker compose -f vault/server/docker-compose.yml up -d
BOOTSTRAP_OPERATORS="alice bob" docker compose -f vault/server/docker-compose.yml \
  exec -it -e BOOTSTRAP_OPERATORS vault-init sh /init/bootstrap.sh

# create the identity secrets (idempotent), issue the Agents' credentials
VAULT_ADDR=https://<vault>:8200 ./scripts/vault-seed-identity.sh
VAULT_ADDR=https://<vault>:8200 ./scripts/vault-agent-creds.sh all
```

- **Unseal is automatic.** `vault-init` initializes Vault on first start (1 key share,
  threshold 1) and unseals it every time it finds it sealed, restarts included.
  The key sits in the `vault-init-data` volume on the server. That is a decision
  taken knowingly: with the key next to the data, splitting it would add ceremony
  and no protection, and anyone who owns the whole host owns both.
- **The root token is used once**, by `bootstrap.sh`, and then revoked and deleted.
  Day-to-day administration goes through the operators' userpass accounts.
- **Changing a policy** in `vault/policies/` on a running Vault: `./scripts/vault-apply-policies.sh`
  (no new bootstrap needed).
- **The UI** is enabled at `<VAULT_ADDR>/ui` (login method **Username**). The certificate is
  signed by the private CA, so browsers warn until `ca.pem` is trusted.
- **Rotating a secret:** `vault kv put -mount=secret tpi/identity/<name> ...`; each
  Agent re-renders within its refresh interval (5 min by default). Consumers that
  read the value only at startup (users-service reads the DB password once) need a
  restart. A new `secret_id` for an Agent: run `vault-agent-creds.sh <role>` again.
- **A secret that was never seeded keeps its Agent unhealthy** (`error_on_missing_key`),
  so the consumer does not start with an empty value.
- **Running users-service from an IDE** without Vault keeps working: it reads
  `DB_PASSWORD` / `ADMIN_BOOTSTRAP_PASSWORD` as before, or a Config Tree directory via
  `SPRING_CONFIG_IMPORT=optional:configtree:./dir/`. Spring gives environment
  variables precedence over files, so those two variables must NOT be set wherever
  Vault is the source.

## Not in Vault, on purpose

- **End users' passwords.** They stay BCrypt hashes in `users.password_hash`, verified
  in-process: Vault is not a user store and gains nothing there.
- **`service_clients.secret_hash`** stays in MySQL; Vault holds the clear secret that
  the owning team needs to present, never replaces the hash.
- **`ADMIN_BREAKGLASS_SECRET_HASH`** is not configured in this stack.
- **api-gateway** and **frontend-users** hold no secrets and did not change.
- **Backup and restore of Vault** are deferred.

## Known limits

- **Operators are administrators.** They cannot read `secret/tpi/<team>/*`, but they can write
  policies and assign them, so an operator could grant themselves access. The audit device records
  it; the protection is trust in the operators and that log, not the policy alone.
- Team members' initial passwords are printed once by `vault-onboard-team.sh`; they travel through a
  private channel and should be changed on first login.

- The JWT kid is the file name `jwks/dev.pem`; rotating the kid means changing the
  template destination and `JWT_ACTIVE_KID` together.
- Tailscale tag capacity (50 on the free plan) counts every microservice, the Vault
  node and every developer laptop that joins with a team key.
