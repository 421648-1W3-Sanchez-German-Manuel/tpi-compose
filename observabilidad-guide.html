Prometheus + Grafana + Redis — Plataforma Gamificada TUP

Patrón Sidecar

Qué es un sidecar

En arquitectura de microservicios, un sidecar es un contenedor auxiliar que se levanta junto al servicio principal y le provee funcionalidad transversal (logging, monitoreo, seguridad, etc.) sin meter ese código en la aplicación. Es como un "asistente" que vive al lado del micro y hace cosas que todos los micros necesitan pero que no son parte del negocio.

Cómo lo usamos nosotros

Prometheus y Grafana son sidecars compartidos. No van dentro de cada microservicio — son contenedores separados que se levantan en el mismo compose y se comunican con los micros por la red interna de Docker:

  • Prometheus es un sidecar de monitoreo. Se levanta una vez y scrapeat a todos los micros. Cada micro solo necesita exponer /actuator/prometheus — no tiene que configurar nada de Prometheus adentro.
  • Grafana es un sidecar de visualización. Se levanta una vez, se conecta a Prometheus, y muestra los datos de todos los micros en un solo dashboard.

La alternativa sería meter un agente de Prometheus dentro de cada contenedor Java, pero eso duplica configuración, consumo de memoria, y complejidad. Con el sidecar, el micro solo expone un endpoint y el sidecar se encarga del resto.

Topología de redes

Las redes de Docker definen quién puede hablar con quién:

navegador ──► nginx :3000 ──► api-gateway ──► users / echo / los que vengan
              [tpi-edge]      [tpi-platform]

tpi-front     nginx + el front. No comparte red con el gateway.
tpi-edge      nginx + api-gateway. Nada más entra acá.
tpi-platform  gateway + eureka + kafka + los micros + prometheus + grafana.
              ES LA RED COMPARTIDA: los otros equipos se enganchan acá.
tpi-data      mysql + redis + quien tenga derecho a leerlos.

Prometheus y Grafana están en tpi-platform para poder scrapear a los micros. Redis está en tpi-data porque es infraestructura de datos.

Redis en nuestra implementación

Por qué usamos Redis

En una arquitectura de microservicios, cuando un request viaja de api-gateway a users-service, ese recorrido queda registrado en un traceId que genera Micrometer/OpenTelemetry. El problema es que ese traceId vive en la memoria del proceso Java y se pierde si nadie lo persiste. Nosotros necesitamos que el dev-mailbox (un servicio Node.js separado) pueda leer esos traces para mostrarlos en la UI de logs. Redis resuelve exactamente eso: es un canal intermedio donde el gateway escribe cada trace inter-micro, y el mailbox lo lee después.

Qué es InterMicroTraceFilter

Es un filtro de Spring Cloud Gateway que se ejecuta en cada request que pasa por el gateway (order 75). Su trabajo es:

  1. Detectar si el request es interno (viene de otro micro, no del browser). Si es del browser, lo ignora.
  2. Extraer el traceId del span activo de Micrometer (el ID que identifica esta request de forma única en toda la cadena de micros).
  3. Extraer el origen del claim type del JWT — esto le dice quién hizo el request.
  4. Armar un JSON con: traceId, origen, destino (el micro destino), timestamp, path, method, y otros campos.
  5. Escribir ese JSON a Redis usando LPUSH (lo pone al inicio de la lista) y luego LTRIM para que la lista nunca tenga más de 200 entradas.
Cómo funciona el flujo completo

El recurso en Redis se llama intermicro:trace y es una lista. Cada entry es un JSON con la traza de un request inter-micro. Así se ve el flujo:

Request: users-service → api-gateway → users-service
                                  ↓
              InterMicroTraceFilter detecta el request interno
                                  ↓
              Arma el JSON con traceId, origen, destino, etc.
                                  ↓
              LPUSH intermicro:trace {JSON}    ← lo pone al inicio
              LTRIM intermicro:trace 0 199     ← mantiene solo los últimos 200
                                  ↓
              dev-mailbox lee con LRANGE intermicro:trace 0 -1
              y lo muestra en /dev/logs

¿Por qué solo los últimos 200? Para que Redis no crezca infinitamente. Si tuvieras 1000 micros haciendo 100 requests por segundo, la lista crecería sin control. El LTRIM garantiza que siempre haya como máximo 200 entradas, y las más viejas se descartan automáticamente.

Verificar que Redis funciona correctamente
# Entrar al CLI de Redis
docker exec -it tpi-redis redis-cli

# Ver cuántas entradas hay en la lista (debería ser ≤200)
LLEN intermicro:trace

# Ver las últimas 5 entradas
LRANGE intermicro:trace 0 4

# Verificar que es una lista (no un string u otro tipo)
TYPE intermicro:trace

# Ver cuánta memoria usa Redis
INFO memory

Si LLEN devuelve 0, significa que no hubo requests inter-micros todavía o que el mailbox los consumió. Si devuelve 200, la lista está llena (como debe ser).

Prometheus

¿Qué es?

Prometheus es un servidor de métricas que funciona como un "recolector pasivo". No recibe eventos — en su lugar, cada 15 segundos hace un request HTTP a cada microservicio al endpoint /actuator/prometheus, que expone Spring Boot con la dependencia micrometer-registry-prometheus. Prometheus parsea esa respuesta y guarda las métricas en su propia base de datos optimizada para series de tiempo.

Métrica clave: http_server_requests_seconds_count

Esta métrica es la más importante para nosotros. Cada vez que llega un HTTP request a cualquier endpoint del micro, Spring Boot incrementa un contador con este nombre. Los labels (etiquetas) que trae son:

  • method: GET, POST, PUT, DELETE
  • uri: el path del endpoint (ej: /api/v1/users)
  • status: código HTTP de respuesta (200, 404, 500, etc.)
  • outcome: SUCCESS, CLIENT_ERROR, SERVER_ERROR

En Grafana usamos esta métrica para graficar: requests por segundo, distribución de códigos de respuesta, y tiempo promedio de respuesta.

Cómo descubre micros (Docker Service Discovery)

En vez de listar manualmente cada microservicio en un archivo de configuración, Prometheus se conecta al socket de Docker y busca contenedores cuyo nombre empiece con tpi-*. Esto significa que si mañana agregás un tpi-games-service que exponga /actuator/prometheus, Prometheus lo detecta automáticamente sin tocar nada.

# prometheus.yml — la parte relevante
scrape_configs:
  - job_name: "docker"
    docker_sd_configs:
      - host: unix:///var/run/docker.sock
        filters:
          - name: name
            values: ["tpi-*"]
Verificar métricas en Prometheus
http://localhost:9090/targets      # ver que los targets estén UP
http://localhost:9090/graph        # query manual de métricas
http://localhost:9090/api/v1/targets  # JSON con estado de cada target

Grafana

¿Qué es?

Grafana es una herramienta de visualización. Se conecta a Prometheus como "datasource" y te permite crear dashboards con gráficos. Nosotros ya creamos un dashboard con 8 paneles que muestra todo lo relevante de los microservicios Spring Boot.

Conexión con Prometheus (auto-provisioned)

Cuando levantás docker compose up, Grafana carga automáticamente dos archivos que ya creamos:

  • Datasource → monitoring/grafana/provisioning/datasources/prometheus.yml le dice a Grafana que se conecte a http://prometheus:9090
  • Dashboard → monitoring/grafana/dashboards/spring-boot.json es el JSON con los 8 paneles

No hace falta configurar nada a mano. Al abrir Grafana, el dashboard ya está ahí con datos.

Scrape de micros en Prometheus

Cómo funciona

Prometheus usa Docker Service Discovery para conectarse al socket de Docker y descubrir contenedores. Cada job en prometheus.yml tiene un filtro regex que matchea un contenedor específico por nombre. Actualmente hay dos jobs: uno para tpi-api-gateway y otro para tpi-users-service.

La convención tpi-* es la que elegimos nosotros. Podría ser cualquier otro prefijo (ej: ms-*, svc-*, o sin prefijo). Lo que importa es que el regex en prometheus.yml matchee el nombre del contenedor que vos elijas.

ContenedorPuertoMétricas
tpi-api-gateway 8081 HTTP, JVM, GC, CPU
tpi-users-service 8083 HTTP, JVM, GC, CPU
Qué hace cada label en prometheus.yml

Cada job tiene esta estructura:

- job_name: 'api-gateway'
  docker_sd_configs:
    - host: unix:///var/run/docker.sock
  relabel_configs:
    - source_labels: [__meta_docker_container_name]
      regex: /tpi-api-gateway
      action: keep
    - target_label: __address__
      replacement: tpi-api-gateway:8081
    - target_label: __metrics_path__
      replacement: /actuator/prometheus
  • docker_sd_configs → host: unix:///var/run/docker.sock: le dice a Prometheus que se conecte al socket de Docker para descubrir contenedores.
  • source_labels: [__meta_docker_container_name]: toma el nombre del contenedor (ej: /tpi-api-gateway).
  • regex: /tpi-api-gateway: filtra solo el contenedor que matchee este nombre exacto. Los que no matcheen se descartan.
  • action: keep: conserva solo los contenedores que pasaron el filtro anterior.
  • target_label: __address__: sobrescribe la dirección donde Prometheus va a hacer el scrape. Sin esto, Prometheus intentaría scrapear en el puerto interno del contenedor.
  • replacement: tpi-api-gateway:8081: la dirección final — nombre del contenedor y puerto donde está el actuator.
  • target_label: __metrics_path__: el path del endpoint de métricas. Sin esto, Prometheus intentaría scrapear en /metrics por defecto.
  • replacement: /actuator/prometheus: el path correcto de Spring Boot Actuator.
Agregar un micro nuevo

Si mañana agregás un tpi-games-service, hay que tocar monitoring/prometheus.yml y agregar un nuevo job copiando la estructura de los existentes, cambiando el job_name, el regex y el replacement (puerto).

- job_name: 'games-service'
  docker_sd_configs:
    - host: unix:///var/run/docker.sock
  relabel_configs:
    - source_labels: [__meta_docker_container_name]
      regex: /tpi-games-service
      action: keep
    - target_label: __address__
      replacement: tpi-games-service:8085
    - target_label: __metrics_path__
      replacement: /actuator/prometheus

Cada micro también necesita tener /actuator/prometheus abierto (sin auth) en su SecurityConfig.

Limitaciones de memoria

Grafana con 256M puede caer (OOMKilled)

Docker Desktop en Windows le asigna a cada contenedor un límite de memoria. Grafana está configurado con 256M, que puede no alcanzar si tenés muchos dashboards o si el build de otros contenedores consume mucha RAM al mismo tiempo. Cuando Grafana se queda sin memoria, Docker lo mata (OOMKilled) y el contenedor se reinicia.

Cómo saber si es OOMKilled:

docker inspect tpi-grafana --format='{{.State.OOMKilled}}'
# true = se quedó sin memoria y Docker lo mató

Solución 1: Subir el límite en docker-compose.yml:

deploy:
  resources:
    limits:
      memory: 512M   # era 256M

Solución 2: Asignar más memoria general a Docker Desktop: Settings → Resources → Memory → 4GB o más.

Prometheus también consume memoria

Prometheus no tiene límite hard configurado en este compose. Si el host se queda sin RAM, puede ser Prometheus o cualquier otro servicio. Para verificar cuánto consume cada uno:

docker stats --no-stream tpi-prometheus tpi-grafana

Resumen

Qué implementamos
  • Redis + InterMicroTraceFilter: persiste traces de requests inter-micros para que el mailbox pueda mostrarlos en la UI
  • Prometheus: recolecta métricas de cada micro cada 15s vía /actuator/prometheus
  • Grafana: visualiza las métricas con 8 paneles, auto-provisionado sin config manual
  • Docker Service Discovery: Prometheus se conecta al socket de Docker para descubrir contenedores
  • Seguridad: el endpoint /actuator/prometheus está abierto (no requiere auth) para que Prometheus pueda scrapearlo
